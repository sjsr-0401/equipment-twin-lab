# 000. 프로그램 진입점부터 WPF 화면이 뜨기까지

이 문서가 코드 독해의 진짜 시작점이다.

이전 `001-core-state-machine.md`는 “Core 로직의 시작점”이다. 하지만 Visual Studio에서 F5를 눌렀을 때 프로그램이 실제로 어디서 시작하는지 보려면 이 문서를 먼저 봐야 한다.

읽을 파일:

```text
src/EquipmentTwin.Hmi.Wpf/EquipmentTwin.Hmi.Wpf.csproj
src/EquipmentTwin.Hmi.Wpf/App.xaml
src/EquipmentTwin.Hmi.Wpf/App.xaml.cs
src/EquipmentTwin.Hmi.Wpf/MainWindow.xaml
src/EquipmentTwin.Hmi.Wpf/MainWindow.xaml.cs
src/EquipmentTwin.Hmi.Wpf/ViewModels/OperatorConsoleViewModel.cs
src/EquipmentTwin.Hmi.Wpf/Services/MolyAldRecipeService.cs
src/EquipmentTwin.Hmi.Wpf/Models/StepRowViewModel.cs
src/EquipmentTwin.Hmi.Wpf/ViewModels/ObservableObject.cs
src/EquipmentTwin.Hmi.Wpf/ViewModels/RelayCommand.cs
```

참고로 실제 `Main()`은 직접 작성한 파일이 아니라 빌드 중 생성된다.

생성 파일:

```text
src/EquipmentTwin.Hmi.Wpf/obj/Release/net8.0-windows/App.g.cs
```

`obj` 폴더는 빌드 생성물이므로 수정하면 안 된다. 읽기만 한다.

## 1. Visual Studio에서 F5를 누르면 무슨 일이 일어나나

사용자가 Visual Studio에서 WPF 프로젝트를 Startup Project로 잡고 F5를 누르면 큰 흐름은 이렇다.

```text
1. Visual Studio가 WPF 프로젝트를 빌드한다.
2. XAML 파일에서 숨겨진 C# 코드가 생성된다.
3. 생성된 App.g.cs 안의 Main()이 실행된다.
4. Main()이 App 객체를 만든다.
5. App.InitializeComponent()가 App.xaml 설정을 읽는다.
6. App.xaml의 StartupUri 때문에 MainWindow.xaml이 열린다.
7. MainWindow 생성자가 실행된다.
8. MainWindow.InitializeComponent()가 화면 컨트롤을 만든다.
9. MainWindow가 OperatorConsoleViewModel을 DataContext로 연결한다.
10. OperatorConsoleViewModel 생성자가 실행된다.
11. Command, Timer, Recipe, Timeline이 준비된다.
12. XAML Binding이 ViewModel 값을 읽어 화면에 표시한다.
```

즉 WPF 실행의 핵심 흐름은 아래다.

```text
App.g.cs Main()
  -> App.xaml
  -> MainWindow.xaml
  -> MainWindow.xaml.cs
  -> OperatorConsoleViewModel
  -> MolyAldRecipeService
  -> MolyAldRunner(Core)
  -> MolyAldTimelineDocument
  -> XAML Binding
```

이제 이 흐름을 파일별로 읽는다.

## 2. `EquipmentTwin.Hmi.Wpf.csproj`

먼저 프로젝트 파일부터 본다.

코드:

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>WinExe</OutputType>
    <TargetFramework>net8.0-windows</TargetFramework>
    <UseWPF>true</UseWPF>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <EnableWindowsTargeting>true</EnableWindowsTargeting>
  </PropertyGroup>

  <ItemGroup>
    <ProjectReference Include="..\EquipmentTwin.Core\EquipmentTwin.Core.csproj" />
  </ItemGroup>

  <ItemGroup>
    <Content Include="..\..\processes\public-moly-ald-metallization.json">
      <Link>processes\public-moly-ald-metallization.json</Link>
      <CopyToOutputDirectory>PreserveNewest</CopyToOutputDirectory>
    </Content>
  </ItemGroup>
</Project>
```

### 줄 단위 해설

| 코드 | 설명 |
|---|---|
| `<Project Sdk="Microsoft.NET.Sdk">` | 이 프로젝트가 .NET SDK 방식 프로젝트라는 뜻이다. |
| `<OutputType>WinExe</OutputType>` | 콘솔창이 아니라 Windows GUI 프로그램으로 빌드한다. WPF 앱이라서 이 설정이 맞다. |
| `<TargetFramework>net8.0-windows</TargetFramework>` | Windows 전용 .NET 8 앱이라는 뜻이다. WPF는 Windows 전용이다. |
| `<UseWPF>true</UseWPF>` | 이 프로젝트가 WPF XAML 빌드 기능을 사용한다는 뜻이다. 이 설정 때문에 XAML에서 `App.g.cs`, `MainWindow.g.cs` 같은 생성 코드가 만들어진다. |
| `<Nullable>enable</Nullable>` | C# nullable reference type 검사를 켠다. `string?`처럼 null 가능 여부를 코드에 표현한다. |
| `<ImplicitUsings>enable</ImplicitUsings>` | 자주 쓰는 using을 자동으로 넣어준다. |
| `<EnableWindowsTargeting>true</EnableWindowsTargeting>` | Windows targeting을 명시적으로 허용한다. |
| `<ProjectReference ... EquipmentTwin.Core.csproj />` | WPF 프로젝트가 Core 프로젝트를 참조한다. 그래서 WPF에서 `MolyAldRunner`, `ManualClock` 같은 Core 타입을 쓸 수 있다. |
| `<Content Include="..\..\processes\public-moly-ald-metallization.json">` | 공정 recipe JSON을 WPF 앱 출력 폴더에 포함한다. |
| `<Link>processes\public-moly-ald-metallization.json</Link>` | 출력 폴더에서는 이 파일이 `processes/...json` 경로처럼 보이게 만든다. |
| `<CopyToOutputDirectory>PreserveNewest</CopyToOutputDirectory>` | JSON 파일이 새로워졌을 때만 출력 폴더로 복사한다. |

### 왜 이 파일이 진입점 독해에 중요한가

이 파일은 “무엇이 실행 가능한 프로그램인가”를 정한다.

`EquipmentTwin.Core`는 class library라 직접 실행되지 않는다.

`EquipmentTwin.Hmi.Wpf`는 `WinExe`라 직접 실행된다.

그래서 Visual Studio에서 UI를 보며 디버깅할 때는 WPF 프로젝트가 시작점이다.

## 3. 진짜 `Main()`은 어디 있는가

WPF 프로젝트에는 보통 직접 작성한 `Program.cs`가 없다.

대신 WPF 빌드가 `App.xaml`을 읽어서 `App.g.cs`를 생성한다.

생성된 코드 일부:

```csharp
public static void Main() {
    EquipmentTwin.Hmi.Wpf.App app = new EquipmentTwin.Hmi.Wpf.App();
    app.InitializeComponent();
    app.Run();
}
```

### 이 코드의 의미

| 코드 | 설명 |
|---|---|
| `public static void Main()` | 프로그램의 실제 시작 함수다. |
| `new EquipmentTwin.Hmi.Wpf.App()` | WPF Application 객체를 만든다. |
| `app.InitializeComponent()` | `App.xaml` 내용을 읽고 적용한다. 여기서 `StartupUri`가 설정된다. |
| `app.Run()` | WPF 메시지 루프를 시작한다. 이 함수가 실행되면 창이 뜨고, 버튼 클릭/타이머/화면 갱신 같은 UI 이벤트를 계속 처리한다. |

### 왜 `App.g.cs`를 수정하면 안 되나

파일 상단에 이런 주석이 있다.

```text
<auto-generated>
This code was generated by a tool.
Changes to this file may cause incorrect behavior and will be lost if the code is regenerated.
</auto-generated>
```

뜻:

```text
이 파일은 빌드가 자동 생성한다.
수정해도 다음 빌드 때 사라진다.
```

그래서 실제로 고칠 파일은 `App.xaml`, `MainWindow.xaml`, `MainWindow.xaml.cs`다.

## 4. `App.xaml`

코드:

```xml
<Application x:Class="EquipmentTwin.Hmi.Wpf.App"
             xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
             xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
             StartupUri="MainWindow.xaml">
    <Application.Resources>
    </Application.Resources>
</Application>
```

### 줄 단위 해설

| 코드 | 설명 |
|---|---|
| `<Application ...>` | WPF 앱 전체를 나타내는 루트 XAML이다. |
| `x:Class="EquipmentTwin.Hmi.Wpf.App"` | 이 XAML이 C#의 `App` partial class와 연결된다는 뜻이다. |
| `xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"` | WPF 기본 컨트롤 namespace다. `Window`, `Button`, `Grid` 같은 것을 쓰게 해준다. |
| `xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"` | XAML 언어 자체의 namespace다. `x:Class` 같은 문법이 여기서 온다. |
| `StartupUri="MainWindow.xaml"` | 앱이 시작되면 `MainWindow.xaml` 창을 열라는 설정이다. |
| `<Application.Resources>` | 앱 전체에서 공유할 resource를 넣는 곳이다. 현재는 비어 있다. |

### 가장 중요한 줄

```xml
StartupUri="MainWindow.xaml"
```

이 줄 때문에 `app.Run()` 이후 `MainWindow`가 생성된다.

## 5. `App.xaml.cs`

코드:

```csharp
using System.Windows;

namespace EquipmentTwin.Hmi.Wpf;

public partial class App : Application
{
}
```

### 줄 단위 해설

| 코드 | 설명 |
|---|---|
| `using System.Windows;` | WPF의 `Application` 타입을 쓰기 위해 필요하다. |
| `namespace EquipmentTwin.Hmi.Wpf;` | 이 클래스가 WPF 프로젝트 namespace에 속한다. |
| `public partial class App : Application` | `App` 클래스가 WPF `Application`을 상속한다. `partial`이라 XAML에서 생성된 코드와 합쳐진다. |
| `{ }` | 현재 직접 추가한 앱 시작 로직은 없다. |

### partial이 중요한 이유

`App` 클래스는 두 조각으로 나뉜다.

```text
App.xaml.cs
App.g.cs
```

둘 다 `partial class App`이기 때문에 컴파일 시 하나의 클래스로 합쳐진다.

이것이 WPF XAML과 C# code-behind가 연결되는 방식이다.

## 6. `MainWindow.xaml`

`App.xaml`의 `StartupUri` 때문에 WPF는 `MainWindow.xaml`을 연다.

파일 첫 부분:

```xml
<Window x:Class="EquipmentTwin.Hmi.Wpf.MainWindow"
        xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
        xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
        Title="Equipment Twin Lab - WPF Operator Console"
        Width="1380"
        Height="820"
        MinWidth="1180"
        MinHeight="720"
        Background="{Binding PageBackground}"
        FontFamily="Segoe UI">
```

### 줄 단위 해설

| 코드 | 설명 |
|---|---|
| `<Window ...>` | 이 XAML 파일의 루트가 WPF Window라는 뜻이다. |
| `x:Class="EquipmentTwin.Hmi.Wpf.MainWindow"` | 이 XAML이 C#의 `MainWindow` partial class와 연결된다. |
| `Title="..."` | Windows 창 제목이다. |
| `Width="1380"` / `Height="820"` | 기본 창 크기다. |
| `MinWidth` / `MinHeight` | 창을 너무 작게 줄이지 못하게 한다. |
| `Background="{Binding PageBackground}"` | 창 배경색을 ViewModel의 `PageBackground` property에서 가져온다. |
| `FontFamily="Segoe UI"` | 화면 전체 기본 폰트다. |

### 여기서 처음 등장하는 Binding

```xml
Background="{Binding PageBackground}"
```

이 뜻:

```text
MainWindow의 DataContext에서 PageBackground라는 property를 찾아서 Background에 넣어라.
```

그런데 이 시점에는 아직 DataContext가 없다.

DataContext는 `MainWindow.xaml.cs` 생성자에서 연결된다.

## 7. `MainWindow.xaml.cs`

코드:

```csharp
using System.Windows;
using EquipmentTwin.Hmi.Wpf.ViewModels;

namespace EquipmentTwin.Hmi.Wpf;

public partial class MainWindow : Window
{
    public MainWindow()
    {
        InitializeComponent();
        DataContext = new OperatorConsoleViewModel();
    }
}
```

### 줄 단위 해설

| 코드 | 설명 |
|---|---|
| `using System.Windows;` | `Window` 타입을 쓰기 위해 필요하다. |
| `using EquipmentTwin.Hmi.Wpf.ViewModels;` | `OperatorConsoleViewModel`을 쓰기 위해 필요하다. |
| `public partial class MainWindow : Window` | XAML과 연결되는 창 클래스다. WPF Window를 상속한다. |
| `public MainWindow()` | 창이 만들어질 때 실행되는 생성자다. |
| `InitializeComponent();` | XAML을 읽어서 실제 WPF 컨트롤 객체들을 만든다. |
| `DataContext = new OperatorConsoleViewModel();` | 이 창의 Binding 대상 객체를 ViewModel로 설정한다. |

### `InitializeComponent()`가 하는 일

직접 작성한 메서드가 아니다.

WPF가 XAML을 기반으로 생성한 partial class 쪽에 들어 있다.

역할:

```text
1. MainWindow.xaml을 읽는다.
2. Grid, Border, TextBlock, Button, DataGrid 같은 컨트롤을 만든다.
3. Resource와 Style을 준비한다.
4. Binding 식을 준비한다.
```

### 왜 DataContext가 중요하나

XAML에는 이런 코드가 많다.

```xml
<TextBlock Text="{Binding Title}"/>
<Button Command="{Binding StartCommand}"/>
<ProgressBar Value="{Binding TimelineProgress, Mode=OneWay}"/>
```

이 Binding들은 전부 DataContext를 기준으로 property를 찾는다.

여기서는:

```csharp
DataContext = new OperatorConsoleViewModel();
```

그래서 XAML은 `OperatorConsoleViewModel`에서 값을 찾는다.

## 8. `OperatorConsoleViewModel` 생성 직전 필드 초기화

`new OperatorConsoleViewModel()`을 실행하면 생성자 본문보다 먼저 field 초기화가 일어난다.

중요한 필드:

```csharp
private readonly MolyAldRecipeService recipeService = new();
private readonly MolyAldRunner runner = new(new ManualClock(new DateTimeOffset(2026, 7, 1, 0, 0, 0, TimeSpan.Zero)));
private readonly DispatcherTimer playbackTimer;
private MolyAldRecipe? recipe;
private MolyAldTimelineDocument? timeline;
private int currentStepIndex;
private bool isRunning;
private bool isAlarmActive;
private string selectedFaultScenario = string.Empty;
```

### 줄 단위 해설

| 코드 | 설명 |
|---|---|
| `recipeService = new()` | JSON recipe를 읽어오는 service를 만든다. |
| `runner = new(...)` | Core의 ALD 공정 실행기를 만든다. |
| `ManualClock(...)` | 공정 timeline을 deterministic하게 만들기 위해 고정 시작 시간을 넣는다. |
| `playbackTimer` | START를 눌렀을 때 timeline을 자동으로 한 step씩 넘기는 WPF timer다. 생성자에서 초기화한다. |
| `recipe` | 로드된 ALD recipe를 보관한다. 아직 없을 수 있으므로 nullable이다. |
| `timeline` | 화면에 보여줄 ALD 실행 timeline이다. |
| `currentStepIndex` | 현재 화면이 보고 있는 timeline step 번호다. |
| `isRunning` | 자동 재생 중인지 여부다. |
| `isAlarmActive` | fault replay 상태인지 여부다. |
| `selectedFaultScenario` | ComboBox에서 선택된 fault scenario 이름이다. |

### 여기서 Core가 처음 연결된다

```csharp
private readonly MolyAldRunner runner = new(...);
```

이 줄에서 WPF가 Core의 공정 실행기를 가진다.

즉 화면은 직접 공정을 계산하지 않는다.

```text
WPF ViewModel은 Core runner를 호출한다.
Core runner가 timeline을 만든다.
WPF는 timeline을 화면에 표시한다.
```

## 9. `OperatorConsoleViewModel` 생성자

코드:

```csharp
public OperatorConsoleViewModel()
{
    StartCommand = new RelayCommand(Start);
    PauseCommand = new RelayCommand(Pause);
    ResetCommand = new RelayCommand(Reset);
    FaultReplayCommand = new RelayCommand(FaultReplay);
    StepForwardCommand = new RelayCommand(StepForward);
    OpenUnityViewerCommand = new RelayCommand(OpenUnityViewer);

    playbackTimer = new DispatcherTimer
    {
        Interval = TimeSpan.FromMilliseconds(750)
    };
    playbackTimer.Tick += (_, _) => StepForwardFromTimer();

    LoadRecipeAndTimeline();
}
```

### 줄 단위 해설

| 코드 | 설명 |
|---|---|
| `StartCommand = new RelayCommand(Start);` | START 버튼이 눌리면 `Start()` 메서드를 실행하도록 연결한다. |
| `PauseCommand = new RelayCommand(Pause);` | STOP 버튼이 눌리면 `Pause()`를 실행한다. |
| `ResetCommand = new RelayCommand(Reset);` | RESET 버튼이 눌리면 `Reset()`을 실행한다. |
| `FaultReplayCommand = new RelayCommand(FaultReplay);` | FAULT REPLAY 버튼이 눌리면 `FaultReplay()`를 실행한다. |
| `StepForwardCommand = new RelayCommand(StepForward);` | STEP 버튼이 눌리면 `StepForward()`를 실행한다. |
| `OpenUnityViewerCommand = new RelayCommand(OpenUnityViewer);` | Unity viewer folder 버튼이 눌리면 폴더를 연다. |
| `playbackTimer = new DispatcherTimer` | WPF UI thread에서 동작하는 timer를 만든다. |
| `Interval = 750ms` | 0.75초마다 Tick 이벤트가 발생하게 한다. |
| `playbackTimer.Tick += ...` | Tick이 발생할 때마다 다음 step으로 이동한다. |
| `LoadRecipeAndTimeline();` | 앱 시작 시 recipe를 읽고 정상 timeline을 만든다. |

### 여기서 화면 버튼과 코드가 연결된다

XAML 버튼:

```xml
<Button Content="START" Command="{Binding StartCommand}"/>
```

ViewModel:

```csharp
StartCommand = new RelayCommand(Start);
```

RelayCommand:

```csharp
public void Execute(object? parameter)
{
    execute();
}
```

흐름:

```text
사용자가 START 클릭
  -> WPF가 StartCommand.Execute() 호출
  -> RelayCommand가 Start() 호출
  -> ViewModel Start() 실행
```

## 10. `RelayCommand`

코드:

```csharp
public sealed class RelayCommand : ICommand
{
    private readonly Action execute;
    private readonly Func<bool>? canExecute;

    public RelayCommand(Action execute, Func<bool>? canExecute = null)
    {
        this.execute = execute ?? throw new ArgumentNullException(nameof(execute));
        this.canExecute = canExecute;
    }

    public event EventHandler? CanExecuteChanged;

    public bool CanExecute(object? parameter)
    {
        return canExecute?.Invoke() ?? true;
    }

    public void Execute(object? parameter)
    {
        execute();
    }

    public void RaiseCanExecuteChanged()
    {
        CanExecuteChanged?.Invoke(this, EventArgs.Empty);
    }
}
```

### 핵심만 이해하기

`RelayCommand`는 버튼 클릭을 ViewModel 메서드로 연결하는 어댑터다.

WPF Button은 `ICommand`를 실행할 줄 안다.

하지만 ViewModel의 `Start()`는 그냥 C# method다.

그래서 둘 사이를 이어주는 객체가 필요하다.

```text
Button
  -> ICommand
  -> RelayCommand
  -> Start/Pause/Reset/FaultReplay
```

### 코드 해설

| 코드 | 설명 |
|---|---|
| `private readonly Action execute;` | 실제 실행할 메서드를 저장한다. 예: `Start` |
| `private readonly Func<bool>? canExecute;` | 실행 가능 여부를 판단하는 선택 함수다. 현재 대부분 null이라 항상 실행 가능하다. |
| `execute ?? throw ...` | 실행 함수가 null이면 명령으로 쓸 수 없으므로 예외를 던진다. |
| `CanExecute` | 버튼이 실행 가능한지 WPF가 물어볼 때 호출한다. |
| `Execute` | 버튼 클릭 시 호출된다. 내부에서 `execute()`를 실행한다. |
| `RaiseCanExecuteChanged` | 나중에 버튼 활성/비활성 상태가 바뀌었음을 WPF에 알릴 때 쓴다. |

## 11. `LoadRecipeAndTimeline()`

ViewModel 생성자 마지막에서 이 메서드가 호출된다.

코드:

```csharp
private void LoadRecipeAndTimeline()
{
    try
    {
        recipe = recipeService.LoadRecipe();
        FaultScenarios.Clear();
        foreach (var fault in recipe.FaultScenarios)
        {
            FaultScenarios.Add(fault.Name);
        }

        selectedFaultScenario = FaultScenarios.FirstOrDefault(name =>
            string.Equals(name, "precursor-dose-timeout", StringComparison.OrdinalIgnoreCase))
            ?? FaultScenarios.FirstOrDefault()
            ?? string.Empty;
        OnPropertyChanged(nameof(SelectedFaultScenario));

        LoadNormalTimeline();
        AddLog("SYSTEM", "WPF HMI ready");
    }
    catch (Exception ex)
    {
        AddLog("LOAD ERROR", ex.Message);
    }
}
```

### 줄 단위 흐름

```text
1. recipeService.LoadRecipe()로 JSON recipe를 읽는다.
2. recipe 안의 FaultScenarios를 ComboBox 목록에 넣는다.
3. 기본 fault scenario를 precursor-dose-timeout으로 잡는다.
4. SelectedFaultScenario가 바뀌었다고 UI에 알린다.
5. 정상 공정 timeline을 만든다.
6. OperatorLog에 SYSTEM 로그를 남긴다.
7. 실패하면 LOAD ERROR 로그를 남긴다.
```

### 왜 try/catch가 있나

Recipe JSON을 못 찾거나 JSON parsing에 실패하면 앱이 바로 죽을 수 있다.

현재는 죽이는 대신 OperatorLog에 에러를 보여준다.

이것은 HMI에서 중요하다.

```text
프로그램이 조용히 죽는 것보다,
화면에 무엇이 실패했는지 보여주는 편이 디버깅에 낫다.
```

## 12. `MolyAldRecipeService.LoadRecipe()`

코드:

```csharp
public MolyAldRecipe LoadRecipe()
{
    var recipePath = ResolveRecipePath();
    var json = File.ReadAllText(recipePath);
    return MolyAldRecipe.FromJson(json);
}
```

### 줄 단위 해설

| 코드 | 설명 |
|---|---|
| `ResolveRecipePath()` | recipe JSON 파일 위치를 찾는다. |
| `File.ReadAllText(recipePath)` | JSON 파일 내용을 문자열로 읽는다. |
| `MolyAldRecipe.FromJson(json)` | JSON 문자열을 Core의 `MolyAldRecipe` 객체로 변환한다. |

### `ResolveRecipePath()`

코드 흐름:

```text
1. AppContext.BaseDirectory/processes/...json 후보 추가
2. Environment.CurrentDirectory/processes/...json 후보 추가
3. 실행 폴더의 부모들을 위로 올라가며 processes/...json 후보 추가
4. 후보 중 실제 존재하는 첫 파일을 반환
5. 못 찾으면 FileNotFoundException 발생
```

왜 이렇게 했나:

```text
Visual Studio에서 실행할 때
dotnet run으로 실행할 때
빌드 출력 폴더에서 실행할 때
repo root에서 실행할 때
경로가 달라질 수 있기 때문이다.
```

## 13. `LoadNormalTimeline()`

코드:

```csharp
private void LoadNormalTimeline()
{
    if (recipe == null)
    {
        return;
    }

    var result = runner.Run(recipe);
    timeline = MolyAldTimelineDocument.FromRunResult(result);
    currentStepIndex = 0;
    RefreshStepRows();
    RefreshComputedProperties();
}
```

### 줄 단위 해설

| 코드 | 설명 |
|---|---|
| `if (recipe == null) return;` | recipe가 없으면 timeline을 만들 수 없으므로 중단한다. |
| `runner.Run(recipe)` | Core의 `MolyAldRunner`가 recipe를 실행한다. 여기서 공정 step들이 만들어진다. |
| `MolyAldTimelineDocument.FromRunResult(result)` | Core 실행 결과를 UI/Unity가 쓰기 쉬운 timeline 문서로 변환한다. |
| `currentStepIndex = 0` | 화면을 첫 step으로 맞춘다. |
| `RefreshStepRows()` | 아래 debug table에 표시할 row 목록을 다시 만든다. |
| `RefreshComputedProperties()` | XAML Binding 값들이 바뀌었다고 WPF에 알린다. |

### 여기서 Core 공정이 실행된다

WPF가 직접 ALD step을 계산하지 않는다.

```text
WPF ViewModel
  -> runner.Run(recipe)
  -> Core MolyAldRunner
  -> MolyAldRunResult
  -> MolyAldTimelineDocument
  -> WPF Binding
```

## 14. `RefreshStepRows()`

코드:

```csharp
private void RefreshStepRows()
{
    Steps.Clear();
    if (timeline == null)
    {
        return;
    }

    foreach (var step in timeline.Steps)
    {
        Steps.Add(new StepRowViewModel(step));
    }
}
```

### 줄 단위 해설

| 코드 | 설명 |
|---|---|
| `Steps.Clear()` | 기존 DataGrid row를 지운다. |
| `if (timeline == null) return;` | timeline이 없으면 표시할 row가 없다. |
| `foreach (var step in timeline.Steps)` | Core가 만든 timeline step을 하나씩 돈다. |
| `Steps.Add(new StepRowViewModel(step))` | Core step을 WPF table 표시용 row 객체로 바꿔 추가한다. |

### 왜 `StepRowViewModel`이 필요한가

Core의 `MolyAldTimelineStep`은 공정 데이터다.

DataGrid에는 사람이 보기 좋은 문자열이 필요하다.

예:

```text
Core value:
MolyAldProcessStep.DoseMetalPrecursor

화면 표시:
Dose Precursor
```

이 변환을 `StepRowViewModel`이 담당한다.

## 15. `ObservableObject`와 화면 갱신

코드:

```csharp
public abstract class ObservableObject : INotifyPropertyChanged
{
    public event PropertyChangedEventHandler? PropertyChanged;

    protected bool SetProperty<T>(ref T field, T value, [CallerMemberName] string? propertyName = null)
    {
        if (EqualityComparer<T>.Default.Equals(field, value))
        {
            return false;
        }

        field = value;
        OnPropertyChanged(propertyName);
        return true;
    }

    protected void OnPropertyChanged([CallerMemberName] string? propertyName = null)
    {
        PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(propertyName));
    }
}
```

### 이 클래스가 필요한 이유

WPF Binding은 ViewModel 값이 바뀐 것을 자동으로 알지 못한다.

그래서 ViewModel이 알려줘야 한다.

```text
이 property 값 바뀌었어.
화면 다시 읽어.
```

그 알림 표준이 `INotifyPropertyChanged`다.

### 핵심 흐름

```text
ViewModel 값 변경
  -> OnPropertyChanged("PropertyName")
  -> WPF Binding이 해당 property 다시 읽음
  -> 화면 갱신
```

예:

```csharp
OnPropertyChanged(nameof(CurrentStepName));
```

이 호출이 있어야:

```xml
<TextBlock Text="{Binding CurrentStepName}"/>
```

이 화면을 다시 갱신한다.

## 16. `RefreshComputedProperties()`

코드 일부:

```csharp

    OnPropertyChanged(nameof(RunStateBrush));
```

### 왜 이렇게 많나

`CurrentStepName`, `PressureValue`, `FilmProgress` 같은 property들은 대부분 계산 property다.

예:


그래서 내부 field가 바뀌면 관련 계산 property들을 전부 갱신하라고 알려야 한다.

## 19. Timer가 step을 넘기는 흐름

생성자:

```csharp
playbackTimer.Tick += (_, _) => StepForwardFromTimer();
```

Timer가 750ms마다 호출:

```csharp
private void StepForwardFromTimer()
{
    if (timeline == null || timeline.Steps.Count == 0)
    {
        return;
    }

    if (currentStepIndex < timeline.Steps.Count - 1)
    {
        currentStepIndex++;
    }
    else
    {
        isRunning = false;
        playbackTimer.Stop();
        AddLog("COMPLETE", "normal process sequence complete");
    }

    RefreshComputedProperties();
}
```

흐름:

```text
Timer tick
  -> timeline 없으면 return
  -> 마지막 step 아니면 currentStepIndex 증가
  -> 마지막 step이면 running false, timer stop, COMPLETE 로그
  -> 화면 갱신
```

`currentStepIndex`가 바뀌면 `CurrentStep`이 바뀐다.

그러면 아래 값들이 전부 달라질 수 있다.

```text
CurrentStepName
PressureValue
TemperatureValue
FilmValue
ValveBrush
TimelineProgress
Debug table selection context
```

그래서 `RefreshComputedProperties()`가 필요하다.

## 22. ComboBox fault scenario 선택 흐름

XAML:

```xml
<ComboBox ItemsSource="{Binding FaultScenarios}"
          SelectedItem="{Binding SelectedFaultScenario, Mode=TwoWay, UpdateSourceTrigger=PropertyChanged}"/>
```

ViewModel:

```csharp
public string SelectedFaultScenario
{
    get => selectedFaultScenario;
    set
    {
        if (string.IsNullOrWhiteSpace(value))
        {
            return;
        }

        if (isAlarmActive)
        {
            AddLog("SELECT BLOCKED", $"{value} locked during active alarm");
            OnPropertyChanged();
            RefreshComputedProperties();
            return;
        }

        if (SetProperty(ref selectedFaultScenario, value))
        {
            AddLog("SELECT FAULT", $"{selectedFaultScenario} ready");
            RefreshComputedProperties();
        }
    }
}
```

흐름:

```text
사용자가 ComboBox 선택 변경
  -> SelectedItem TwoWay Binding
  -> SelectedFaultScenario setter 호출
  -> 빈 값이면 무시
  -> 알람 중이면 선택 변경 막고 로그
  -> 정상 상태면 selectedFaultScenario 변경
  -> SELECT FAULT 로그
  -> 화면 갱신
```

여기서 `TwoWay`가 중요하다.

```text
화면에서 선택한 값이 ViewModel로 들어와야 하므로 TwoWay가 맞다.
```

반대로 ProgressBar는 사용자가 값을 입력하는 게 아니므로 `OneWay`가 맞다.
